# Демонстрация на защите

## Подготовка

В корне проекта выполните `make run`, откройте http://127.0.0.1:8080/swagger/ и оставьте рядом [RFC](RFC.md) и [C4-диаграмму](../diagrams/rendered/rfc-b-c4-container.svg).

Стенд полностью локальный. Данные в памяти, Kafka/outbox заменены очередью внутри процесса, провайдеры имитируются. Ядро выбора каналов, переходов и SMS Sender настоящее. Эти границы стоит назвать перед показом.

Проверить весь показ автоматически при запущенном сервере:

```bash
make smoke
# другой адрес:
python3 scripts/smoke.py --url http://127.0.0.1:8090
```

Проверка сбрасывает только данные этого демостенда.

## Маршрут выступления

| Время | Действие | Что объяснить |
| --- | --- | --- |
| 0:00–1:00 | Показать контекст и C4 варианта B | Единый приём, Kafka, оркестратор, постоянное состояние, отправители |
| 1:00–2:00 | Сценарии `push-success`, `failover` | Provider ACCEPTED отличается от ACK; timeout вызывает резерв; A → B только после явного отказа |
| 2:00–3:00 | `retry` | Контакты и публикация результата падают; сохранённый результат предотвращает новую SMS |
| 3:00–4:00 | `late-ack` | Межканальные дубли возможны, подтверждения дедуплицируются, отправка уже ушедшей SMS необратима |
| 4:00–5:00 | `expired`, `all-failed`, `email-only` | EXPIRED, FAILED и SENT имеют разную семантику; ни одно не равно DELIVERED |
| 5:00–6:00 | Метрики и сравнение альтернатив | Почему PostgreSQL/outbox вместо одного Redis SETNX; что ещё проверять перед production |

Готовые сценарии создают новый ID при каждом вызове. Для доказательства идемпотентного приёма используйте ручной запрос ниже.

## Ручной сценарий в Swagger

1. `DELETE /api/demo` → Execute.
2. `POST /api/notifications` → выберите пример **manual**. Сохраните `notification.id`. В ответе `SENDING`, `step_idx=0`, одна push-команда и один таймер. Предпочтения задаются в `profile`; отсутствие `profile` включает все три канала.
3. Повторите то же тело. Ответ `200` вместо `201`, ID тот же, число команд и отправок не меняется.
4. `POST /api/demo/advance` с `{"seconds":10}`.
5. `GET /api/notifications/{id}`: `DELIVERED/sms`, в событиях есть `failover`, отказ агрегатора A и submit в B. Исходный push не был подтверждён.
6. `POST /api/notifications/{id}/receipts` с `{"step_idx":0,"channel":"push","status":"DELIVERED"}`. Это поздний ACK: появляется `cross_channel_duplicate`, новые команды не создаются.
7. Повторите receipt: новый дубль в событиях/метриках не появляется.
8. `POST /api/notifications/{id}/replay`: число provider submissions не растёт.
9. Измените `user_id` в исходном теле при прежнем ключе: получите `409`. Ключ нельзя переиспользовать для другого запроса.
10. Откройте `/metrics`: видны конечные состояния, число принятых провайдерами отправок, подтверждённые межканальные дубли и очередь повторов.

Если хотите увидеть SMS в процессе ожидания, создайте сообщение с `simulation.sms="silent"`. После advance 10 с оно будет `SENDING` на шаге SMS. Replay этого шага переиздаст сохранённый ACCEPTED без новой SMS. Ещё 60 с без DLR переведут план на email и дадут `SENT`.

Все интервалы в HTTP API — секунды. `advance` действует на **все** уведомления стенда и исполняет каждый промежуточный дедлайн, а не только последний. Реальное ожидание не продвигает виртуальные часы.

## То же через curl

Создать:

```bash
curl -sS -i http://127.0.0.1:8080/api/notifications \
  -H 'Content-Type: application/json' \
  -d '{
    "idempotency_key": "defense-manual-001",
    "user_id": 42,
    "category": "TRANSACTIONAL",
    "ttl_seconds": 3600,
    "profile": {
      "preferred_channel": "push",
      "push_ready": true,
      "has_phone": true,
      "has_email": true
    },
    "simulation": {
      "push": "silent",
      "sms": "delivered",
      "sms_primary_down": true
    }
  }'
```

Продвинуть время:

```bash
curl -sS http://127.0.0.1:8080/api/demo/advance \
  -H 'Content-Type: application/json' -d '{"seconds":10}'
```

Подставить ID из ответа:

```bash
curl -sS http://127.0.0.1:8080/api/notifications/NOTIFICATION_ID

curl -sS http://127.0.0.1:8080/api/notifications/NOTIFICATION_ID/receipts \
  -H 'Content-Type: application/json' \
  -d '{"step_idx":0,"channel":"push","status":"DELIVERED"}'

curl -sS -X POST http://127.0.0.1:8080/api/notifications/NOTIFICATION_ID/replay
```

Готовый сценарий одной командой:

```bash
curl -sS -X POST http://127.0.0.1:8080/api/demo/scenarios/retry
```

## Что смотреть в JSON

| Поле | Значение |
| --- | --- |
| `notification.plan` | Порядок каналов, ACK timeout в секундах |
| `notification.step_idx` | Запущенный шаг, нумерация с нуля; -1 если ничего не запускалось |
| `notification.state` | Исход текущей/завершённой обработки |
| `events` | Упорядоченная история решений и подтверждений с виртуальным временем |
| `commands` | Команды, созданные оркестратором; это не счётчик физических отправок |
| `timers` | Действующие дедлайны; после завершения пусто |
| `provider_submissions` | Уникальные принятые отправки в имитаторе провайдера |
| `pending_retries` | Отложенные повторы после временных ошибок |

## Ответы на вероятные вопросы

**Почему не синхронный вызов SMS из платежа?** Доступность и время платежа не должны зависеть от внешнего уведомления. Устойчивый приём отделён от отправки, результат доступен отдельно.

**Почему не достаточно Kafka exactly-once?** Транзакция Kafka не включает внешнюю SMS и состояние PostgreSQL/Redis. Нужны outbox, уникальные ID и согласованный контракт внешнего провайдера.

**Почему Redis SETNX недостаточно?** Флаг может быть установлен до сбоя отправки. Повтор будет подавлен, хотя действие не состоялось. В решении различаются аренда, сохранённый результат и публикация этого результата.

**Гарантируете ли отсутствие дублей?** Повтор одного логического шага подавляется при поддержке идемпотентности провайдером. Между каналами возможен дубль из-за позднего ACK: выбор сделан в пользу доставки. В демо это видно явно.

**Что означает гарантированная доставка, если все каналы упали?** Сохранность, повторяемая обработка и объяснимый конечный исход гарантируются в оговорённой модели отказов. Получение зависит от наличия доступного канала и контакта. Абсолютную физическую доставку при полном отказе внешнего мира система обещать не может.

**Можно ли считать email успешной доставкой?** В прототипе нет подтверждения email. `SENT` означает принятие провайдером; в delivery SLO он не считается подтверждённым успехом.

**Что при таймауте SMS-агрегатора?** Неизвестный исход не равен отказу. Пытаемся сверить/повторить у закреплённого агрегатора с прежним ClientMsgID. Переключение A → B допустимо при подтверждённом непринятии. Отдельный сценарий можно задать через `simulation.sms="unknown_once"` и advance на 35 с.

**Почему PostgreSQL, выдержит ли нагрузку?** Он упрощает транзакционное состояние и координацию. Целевые числа рассчитаны, но не измерены на БД. Нужны испытания outbox, индексов и таймеров; затем при необходимости шардирование по notification_id.

**Что реально работает сейчас?** Оркестратор, sender, идемпотентность, таймеры, receipts, API, сценарии и метрики работают. Хранилище и провайдеры локальные. Kafka/PostgreSQL-адаптеры, реальные SMS, подписи и HA — следующий инженерный этап из RFC.

**Как оценить качество тестов?** Они воспроизводят конкретные сбои и проверяют число отправок/состояния. Race detector проверяет Go-доступ к памяти; проверка реальных блокировок и надёжности кластера требует интеграционного контура.
